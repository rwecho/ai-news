我是在 X 上刷到这条视频的。

文案有点故意撩人：

> 数字人不稀奇。  
> 可互动的数字人也不稀奇。  
> 那如果是带深夜福利、可互动的数字人呢？

视频里的角色叫“小岚”。左边是一个女性数字人，右边有聊天框和几个控制按钮。点一下，她会回应；再点一下，她会换动作、换衣服，甚至切到所谓的夜间模式。

<DriveVideo fileId="1mWEpU9rv_zIY3Se0Gpl5U6t2IGPBRZj4" title="小岚互动数字人原始视频" />

我第一眼也以为这是一个实时生成的数字人系统。把视频放慢以后，感觉事情可能没那么玄。

人物、房间、光线和镜头一直很稳。按钮点下去之后，变化发生得很快，没有看到明显的生成等待，也没有出现实时视频常见的脸部漂移。换装和动作看起来更像是从一组已经准备好的片段里切出来的。

所以我目前更相信下面这条路径：

```text
用户点击按钮
→ 前端改变角色状态
→ 播放对应的图片或短视频
→ 同时更新文字、语音和界面
```

这不是说它“作弊”。如果目标是做一个用户真的愿意点第二次的产品，固定素材往往比每次临时生成更靠谱。稳定、快、便宜，而且出了问题也知道是哪一个状态坏了。

## 先把它当成一个网页，而不是一个模型

做第一版时，最容易走偏的地方，是一上来就研究“用哪个数字人模型”。其实先要解决的是：这个角色到底有哪些状态。

比如：

- idle：站着或坐着等待；
- smile：笑一下；
- wave：挥手；
- speak：说话；
- night：切换到夜间场景；
- change-clothes：换一套衣服。

每个状态可以对应一段几秒钟的视频，也可以只是一个循环播放的短片。用户点“让她笑一下”，网页就切到 smile；点“夜间模式”，网页就切到 night。对用户来说，她做出了回应；对系统来说，只是一次状态切换。

前端可以先用一个很普通的对象把关系写清楚：

```ts
const avatarStates = {
  idle: {
    video: "asset-idle",
    text: "你来了。"
  },
  smile: {
    video: "asset-smile",
    text: "看到你，我心情不错。"
  },
  night: {
    video: "asset-night",
    text: "现在是夜间模式。"
  }
};
```

这里的 video 应该指向产品自己的对象存储或 CDN 地址。点击按钮时，更新 currentState，找到对应的视频和文字，播放就行。第一版甚至不需要上 WebSocket，也不需要自己训练模型。

## 素材要先固定，不然数字人会越做越像不同的人

先做一张角色参考图，把脸型、发型、服装、房间、镜头位置和光线定下来。后面所有素材都围绕这张图做。

建议一开始只准备一小组动作：

```text
idle.mp4
smile.mp4
wave.mp4
speak-01.mp4
speak-02.mp4
night.mp4
change-clothes-01.mp4
```

动作不要贪多。五到八个状态足够做出第一个能玩的 Demo。状态太多，素材之间反而容易穿帮：脸变了、房间变了，用户马上会发现这不是一个角色，只是几张图被放在了同一个网页里。

如果用真人照片或真人视频做角色，要先拿到本人授权。尤其是“深夜模式”这类容易引起误解的内容，不能拿别人的脸直接成人化，也不能让用户上传他人的照片来做暧昧化处理。

## 聊天模型只需要决定“怎么回”和“做什么动作”

如果用户可以自由输入文字，再接一个大语言模型。模型不负责生成整段视频，它只负责返回一句合适的回复，再给出一个情绪和动作。

例如：

```json
{
  "text": "今天心情还不错，你呢？",
  "emotion": "smile",
  "action": "wave"
}
```

网页拿到 action 后，播放 wave；拿到 emotion 后，更新界面颜色或字幕。这样模型和画面分开了，模型说错一句话，不会把整段视频生成链路一起拖垮。

角色提示词也不用写得很长。重点是让它知道自己是谁、能做什么、不能做什么：

```text
你是“小岚”，一个明确为成年人的虚拟角色。
说话自然、简短，带一点调侃，但不要像客服。
不要假装自己是真人。
遇到未成年人、非自愿或违法内容时直接拒绝。
每次回复尽量不超过两句话，并返回 emotion 和 action。
```

语音可以放到第二步。第一版先准备二三十句高频回复，或者用 TTS 现生成。等文字、动作和状态机跑顺了，再处理实时口型。不然一开始就把对话、TTS、口型、视频生成全部接上，排错会变成一锅粥。

## 真实时数字人，难点不在“能不能动”

如果一定要让角色根据任意一句话实时说话，可以研究这些项目：

- [LivePortrait](https://github.com/KwaiVGI/LivePortrait)：用驱动动作控制人像表情和头部运动；
- [EchoMimic](https://badtobest.github.io/EchoMimic/)：通过音频和面部动作生成肖像动画；
- [DH_live](https://github.com/kleinlee/DH_live/)：偏轻量级 2D 视频数字人和网页实时运行。

但它们解决的是“让画面动起来”，不是完整的产品体验。真正上线以后，马上会遇到脸部漂移、长时间运行、全身动作、服装一致性、GPU 成本和并发等问题。

所以我的建议是：先做固定素材版本，确认用户真的愿意和这个角色互动，再把最常用的几个状态换成实时生成。不要为了证明技术能力，一开始就把最难的部分全接进来。

## “深夜模式”本质上仍然是产品边界

从程序角度看，它可能只是一组状态：

```text
普通模式
→ 夜间模式
→ 对应服装或场景
→ 对应语音和动作
```

但这部分不能只当成一个按钮。至少要有年龄确认，不使用未成年人形象，不使用未经授权的真人脸，不允许把别人的照片成人化，也要给用户举报和退出入口。

固定素材在这里还有一个实际好处：你知道用户最终会看到什么，不会让生成模型临场把内容推到不可控的方向。

## 我会怎么做第一版

如果是我来做，不会先训练模型，而是先做一个小网页：

```text
Next.js
+ 一个固定角色
+ 一个房间场景
+ 6 个动作状态
+ 20 条预设回复
+ 一个聊天窗口
+ 对象存储或 CDN
+ 年龄与内容安全控制
```

产品素材可以按这个方式组织。原始工程素材放 Drive 或 MinIO，真正给网页播放的文件则放对象存储/CDN：

```text
小岚互动数字人/
├── 00_人物参考图/
├── 01_普通状态/
├── 02_动作视频/
├── 03_服装状态/
├── 04_语音文件/
├── 05_网页播放版本/
├── 06_版权与授权/
└── manifest.json
```

GitHub 可以保存状态名称、素材路径和展示规则，但不保存视频本体。Drive 里的那份视频属于本次研究的归档素材，不应该直接当成产品的播放服务。等访问量起来，再把播放层放到 CDN 或对象存储，Drive/MinIO 继续保存原始文件和备份。

这条视频真正值得拆的地方，不是“它用了哪个神秘模型”。更可能是有人把几个普通技术拼成了一个很顺的体验：素材提前准备好，模型负责聊天，前端负责切状态，用户每点一下，都能马上得到反馈。

数字人本身未必突然变聪明了。只是网页终于学会了回应。
